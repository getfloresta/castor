# Castor design notes

This document describes Castor's internals: file formats, the bootstrap builder, the
steady-state prover, the persistence and recovery protocol, and the P2P server. For
installation and usage, see the [README](../README.md).

## Hintsfile

`bridge-hints` is a standalone scanner. It reads an unpruned Bitcoin Core datadir directly
through `rust-bitcoinkernel` and uses no RPC connection or credentials. It uses the standard
Bitcoin Core network paths (`$HOME/.bitcoin/signet` for Signet). If `--stop-height` is omitted,
it uses Core's current active-chain tip.

Both `bridge-hints` and the bootstrap builder open the already-synced Core chainstate with
`rust-bitcoinkernel::ChainstateManager` and read blocks through its active chain entries. They
do not run a second sync or reindex.

The scanner keeps the UTXO set for the target height in memory. It assigns per-block indices
only to outputs that are eligible for the Utreexo accumulator. It increments the index only
after excluding:

- OP_RETURN scripts
- scripts larger than 10,000 bytes
- outputs spent in the same block that created them
- the first occurrences of the two historical BIP30-overwritten outputs, at heights 91,722 and
  91,812

### File format

| Field | Encoding |
| --- | --- |
| Magic | `BRLFCT01` (bridge-owned prefix) |
| Stop height | little-endian |
| Eligible-leaf counts | one little-endian `u32` per height, from 1 through the stop height |
| Payload | the unchanged `hintsfile` library payload |

The scanner encodes the completed file to a temporary file and atomically moves it into place.
Raw hintsfiles generated by the library without the prefix are not accepted.

## Parallel flat-forest bootstrap

On Linux, the builder constructs the historical forest directly in a preallocated,
memory-mapped flat file. The build target is the hintsfile's stop height.

### Work distribution

The builder reads the deterministic per-block leaf counts from the hintsfile prefix. From them
it computes every block's leaf offset without reading any block. It then reads each historical
block exactly once while the leaf workers fill the forest, leaf map and header index. Hints
indices are interpreted over Utreexo-eligible outputs in block order. Provably unspendable
outputs and outputs consumed in their creating block are excluded.

By default the CPUs are split evenly between leaf workers and chaser workers.
`--forest-leaf-workers` and `--forest-chaser-workers` override that split.

- **Leaf workers** claim four-height chunks from a shared atomic allocator. Each claim returns
  the next adjacent chunk, so a worker that finishes early immediately moves ahead of the
  others and takes more work. No worker owns a fixed range of the chain.
- **Chasers** hash parent nodes. Each chaser owns a deterministic range that covers at least
  two input pages, unless an entire upper row is smaller than that. Deletions follow these
  rules:
  - If one child is deleted, the surviving sibling is promoted to the parent.
  - If both children are deleted, the parent is marked deleted.
  - Promotion repeats recursively, carrying surviving subtrees up to the roots.

  Independent ranges apply these rules concurrently while leaves are still being published.
  `--forest-spin-iterations` controls how long a chaser spins before it sleeps on the
  publication condition variable.

`--forest-leaf-capacity` raises the initial bottom-row capacity above the bootstrap leaf count.
It must not be lower than the leaf count encoded through the hints stop height. In steady
state, the mapped forest grows automatically when additions exceed that capacity.

Range acquisitions and aggregate build timings are logged at debug level to
`$DATA_DIR/debug.log`. The terminal shows only lifecycle and progress information.

### Forest file format

The forest file has no header. Node `N` starts at byte offset `N * size_of::<ForestNode>()`.
Each node is 33 bytes:

| Bytes | Content |
| --- | --- |
| 0–31 | hash |
| 32 | flags: bit 0 = initialized, bit 1 = spent |

The file is sized for the complete positional space at the required forest height. Unused
positions remain zero.

### Header file and header index

The leaf workers write every 80-byte consensus header at offset
`height * size_of::<SerializedHeader>()` in the header file. The genesis header is at position
zero. They also insert a `block_hash -> height` mapping into the header index.

### Leaf map and header index encoding

Both indexes use the `floresta-db` format v7.

- **Leaf map.**
  - Key: the first 16 bytes of SHA-256 over the 32-byte internal txid followed by the
    little-endian `vout`.
  - Value: the leaf's bottom-row position, as a little-endian `u64`.
  - Only unspent leaves are indexed.
  - A promoted leaf keeps its original bottom-row position permanently. The parent chasers
    never update the map.
- **Header index.**
  - Key: the first 16 bytes of the internal block hash.
  - Value: the height, stored inline as a `u64`.
  - Lookups verify the full hash against the stored header.

The leaf map uses an insert-only range writer. Eligible outputs are written once per block with
`WriteOnlyWriter::put_batch`, and header mappings once per fetched range. The database groups
keys by bucket before CAS publication. Fixed eight-byte positions and heights are stored
inline. Mutable bucket heads stay in memory during construction and are written out during
sync or clean close.

Leaf maps and header indexes with variable-width keys from older versions are incompatible.
Rebuild the bootstrap into fresh output paths before running steady state, and don't mix an old
index with a new forest. On clean completion, the runtime files are synced and closed directly,
without a checkpoint snapshot. Recovery from an interrupted build is not supported.

### Memory

The builder uses `posix_fallocate`, `MADV_WILLNEED` and `MADV_HUGEPAGE`. It also requests
`mlock2(MLOCK_ONFAULT)` so that pages it has touched stay resident. This request only works if
the process has an unlimited memlock limit (`ulimit -l unlimited`, or `LimitMEMLOCK=infinity`
under systemd).

Without that permission, the builder logs a warning and continues using the Linux page cache.
`--forest-no-mlock` turns the request off explicitly. No sysctl changes are required, because
Linux uses otherwise-free RAM for the mapped file. Avoid raising `vm.dirty_ratio` globally: it
can starve the rest of the system, and it only postpones the final writeback rather than
removing it.

## Steady-state prover

Steady state continues from the hintsfile's stop height, using the same forest and leaf map.

### Fetching blocks

Bitcoin Core must run with `txindex=1`. For each height the prover calls `getblock` with
verbosity 3, which returns the block's transactions and every input's prevout in one RPC
response. It makes no extra request for median-time-past, because that value isn't used in
leaf commitments or proofs. Providers without verbosity-3 support fall back to fetching
transactions one at a time.

Cache hits skip prevout reconstruction. The hashes of the blocks that created the spent outputs
come only from the in-memory cache and the persistent header index. Steady-state proving never
calls `getblockhash` for prevouts. A missing height means the bootstrap header files don't
match the forest.

### Proving a block

After resolving the leaf data, the prover:

1. verifies the batch proof,
2. propagates deletions,
3. appends eligible outputs, and
4. checks the resulting roots against a `rustreexo` stump update.

Outputs created and spent in the same block never enter the forest.

Mutation planning uses an `AHashMap` overlay and emits journal output sorted by position.
Independent deletion parents are hashed with Rayon once a row has at least 128 parents. Smaller
rows are hashed on the current thread to avoid scheduling overhead. Hashing of eligible addition
leaves uses the same 128-item parallel threshold. Addition positions don't repeat leaf-map
membership lookups that the serialized block update already guarantees.

### Pollard cache

The steady-state `Pollard` starts from the flat forest's roots and keeps stable bottom
positions for the leaves it remembers.

- **Cached spends** resolve through the Pollard's internal index, without querying the
  persistent leaf map or rereading the leaf hash.
- **Cache misses** are resolved first against pending outpoint updates. The unchanged part of
  the leaf map is then queried in one ordered `batch_fetch`.

The Pollard reports which target and proof positions it doesn't have cached. Only those hashes
are read from the flat forest and ingested. The Pollard is updated immediately and is the
source of truth while journal records are pending.

`--pollard-memory-mib` sets the cache quota (default 250 MiB). Cache eviction doesn't wait for
persistence, because the pending node and outpoint overlays keep later cache misses up to date.

Before fetching sibling spentness, the conversion from bottom positions to proof positions
sorts the live target frontier and removes twins (sibling pairs). Sibling targets merge into
one parent traversal without reading either sibling. The remaining sibling nodes are each
fetched once, in ascending physical-position order. The resulting proof targets keep the
original input order, so they stay aligned with the deletion hashes and leaf data.

### Overlays

The persistent leaf map keeps holding stable bottom positions. Pending forest-node and outpoint
changes, including removals, are overlaid in the foreground. As a result, even a fully evicted
Pollard can prove blocks while the durable forest is behind.

Each overlay entry records the height that produced it. An entry is retired only when that
height is acknowledged, so retiring an earlier block can't discard a later update to the same
node or outpoint. The runtime map gets 1 GiB of append headroom. Older bootstrap maps are
extended in place before they are opened.

### Metrics

Per-block cache metrics, foreground timings and completed `background-persistence` timings are
logged at debug level to `$DATA_DIR/debug.log`. The terminal shows block height, hash, proof
size and important lifecycle events, without timing details.

`steady-state-timings` keeps the aggregate `positions` duration. The accompanying
`steady-state-position-timings` line splits it into these phases:

| Phase | Covers |
| --- | --- |
| `cache` | leaf hashing, cached bottom-position lookup and collection of uncached inputs |
| `leaf_map` | key preparation and the database batch fetch |
| `validation` | decoding index results, resolving overlay entries and checking forest bounds |
| `resolution` | assembling bottom positions, including explicit recovery for missing or invalid entries |
| `traversal` | sorted, detwinned sibling fetching and conversion to canonical proof targets |

`validation` doesn't read forest nodes to recheck spentness, because Bitcoin Core has already
validated the spends.

Each phase has a matching `*_majflt` field. On Linux, these are `RUSAGE_THREAD` major-page-fault
deltas for the proving thread only, excluding background workers. `Some(0)` means no major
faults, and `None` means the counter was unavailable. Faults indicate paging that required I/O,
not every storage wait: database syscalls and writeback stalls don't necessarily increment
them.

Measurements are taken at phase boundaries, not per input. Phase times exclude the overhead of
sampling the counters, so they don't necessarily add up exactly to `positions`.

## Persistence

### Journal

The prover appends complete, page-aligned records to `$DATA_DIR/forest.journal` without
syncing. Each record contains:

- the block identity and the post-block `numleaves`
- changed forest positions, with before/after hashes and flags
- added and removed outpoints, with their stable bottom positions
- the block header and compact proof
- both the physical and the proof forest-row counts

Pending changes stay in the foreground overlay. No forest, leaf-map, header, proof or
proof-index writes happen yet.

### Publication windows

Every **100 new blocks**, the prover submits an immutable journal end offset to the persistence
worker. The worker:

1. flushes the journal,
2. advances the checksummed publication marker in `forest.journal.published`, and
3. flushes that marker.

The marker alternates between two slots, so a torn update can't corrupt it. Later appends may
reach disk while this happens, but they aren't part of the captured publication boundary. No
producer metadata lock is held across the sync.

Only after publication succeeds does the worker:

1. write proofs, headers and proof-index entries,
2. apply the merged forest writes and the block-ordered leaf-map changes,
3. sync those stores, and
4. commit the final applied height.

Notifications and completions follow the applied-height commit, not journal publication.

There is at most one submitted window and one accumulating window, so at most **200 blocks**
can be pending. The earlier 256 MiB pending-memory gate was removed because it could prevent
reaching publication. Memory use now depends on the contents of those bounded windows,
separately from the Pollard cache quota. Journal entries and proof payloads are shared rather
than copied into each queue.

When a prover range completes, it publishes its partial window and waits for it to be applied
before returning. So once the prover catches up to Core's tip, every proof it generated is
available over P2P. In normal operation, even a single newly mined block is published at the
end of its range.

### Applying a window

For each published window, the worker merges the blocks' position-sorted forest deltas. It
writes each touched position exactly once, in ascending physical order, and the last block's
state wins when positions overlap. A heap holds one cursor per non-empty block, instead of
copying or sorting all node states into another window-sized buffer. Leaf-map changes and
compaction boundaries keep block order under the same exclusive lock. The per-block
before/after states in the journal stay unchanged, for rollback and for recovering interrupted
writes.

Journal application and rollback use per-block, key-sorted `batch_delete` and `put_batch`. They
remove the union of affected keys before reinserting them, so replay stays idempotent even
though the database's append-only batch writer keeps duplicate keys.

### Compaction and locking

After applying each steady-state block whose `height % 1_000 == 0`, the background worker:

1. compacts leaf-map pages that are less than half full (16,384 live nodes per 1 MiB page),
2. syncs the forest and database, and
3. publishes completion.

If compaction fails, persistence stops instead of marking the height durable.

The worker holds an exclusive forest lock only during mutation, relocation and compaction, so
foreground lookups can't keep stale node offsets. During the forest/database sync it holds a
shared lock, which lets proof planning and cache misses run concurrently.

A separate storage read/write lock is shared by:

- header reads
- bootstrap batches
- synchronization
- steady-state index replacement and removal

### Header index growth

At startup, the header index keeps 64 MiB of append headroom for its body. If a steady-state
insertion runs out of mapped space, the persistence worker:

1. takes exclusive storage access,
2. fully closes and unmaps the database,
3. adds another 64 MiB of headroom beyond the allocator high-water mark,
4. reopens the database, and
5. retries the insertion once.

Existing header mappings are preserved without restarting or rebuilding, and the growth is
logged. Readers and synchronization wait while the database is remapped. Bootstrap writers
borrow their database handle only for each locked batch.

If the close, growth or reopen fails, the error is returned to persistence and the index is
explicitly marked unavailable, rather than continuing with a stale mapping. Growth doesn't
change allocator page sealing, so synchronization can still leave partially used pages.

### Online forest growth

Online growth doubles the bottom-row capacity without restarting the node:

1. An explicit sync first publishes and applies any partial window.
2. Internal rows are relocated into the enlarged positional layout.
3. The newly exposed bottom positions are cleared before proving continues.

A durable `forest.resize` sidecar file records which relocation phase has been reached. At
startup, an interrupted resize is resumed before the steady-state forest is opened.

Journal records keep their physical forest-row count, so replay and rollback can translate old
node positions into the current layout. Proof-index entries separately keep the logical row
count their targets use, so proofs created before and after a resize stay wire-compatible.

### Proof storage

Proofs for blocks after the hints stop height are appended to `$DATA_DIR/proofs` and indexed by
block hash under `$DATA_DIR/proof-index`. Records contain only targets, proof hashes and compact
leaf data. Bitcoin blocks are fetched from Core and are not stored.

### Shutdown and reorgs

- **Explicit sync and graceful shutdown** also publish partial windows and wait for them to be
  applied. Shutdown writes the clean marker only after all accepted work and all storage are
  synced.
- **Capacity growth and position repair** sync explicitly before their ordered worker
  operations.
- **Reorgs**:
  1. drain the work already submitted,
  2. discard the entire unpublished tail,
  3. roll back published orphan blocks, and
  4. reprove any discarded blocks that are still on the active chain.
- **An ordinary drop or an error** never submits a partial window.

All flushes and durable-store writes happen on background workers. The prover itself only writes
unsynced journal records, although buffered writes can still hit kernel writeback stalls.

### Timing fields

`persistence_enqueue` includes the unsynced journal append and the backpressure at window
boundaries. `background-persistence` reports:

| Field | Covers |
| --- | --- |
| `publication` | journal flush, marker bump and marker flush |
| `apply` | applying the forest and leaf-map changes |
| `state_flush` | syncing the forest and database |
| `proof_store` | writing proofs |
| `header_store` | writing headers |
| `proof_index_write` | writing proof-index entries |
| `height_commit` | committing the applied height |

Its `first_height`, `height` (the last height) and `blocks` fields identify the window, and
durations are totals for the whole window.

## Crash recovery and compatibility

### Startup recovery

At startup, Castor discards every byte beyond the last valid publication boundary, including
complete checksummed records that reached disk. Published records carry enough data to restore
headers and compact proofs, as well as forest and leaf-map changes, if they were interrupted
while being applied. The applied-height checkpoint is separate from the published journal tip.

If publication fails, submissions stop and a clean shutdown is never certified. If it's
uncertain whether a marker flush succeeded, the journal must be reopened.

Opening storage and recovering from a crash run on named startup workers. These include
initializing legacy proof-row metadata and truncating proofs. Startup waits for these workers to
finish before it builds the thread-local Pollard, and the caller issues no recovery flush.

After restoring the available published redo data, startup validates that the proof-index range
is contiguous. Legacy records without proofs keep the previous rollback policy for proof gaps.

Reorgs durably mark published orphan records before restoring old node states, leaf-map entries
and `numleaves`.

### Journal pruning

Pruning keeps at least 144 forward records. Before reclaiming old pages, it advances the replay
floor in both marker slots. Journal offsets stay stable, and runtime compaction no longer
renames the active file. Filesystems that support hole punching reclaim the old spans.
Filesystems that don't keep those bytes allocated, but recovery skips them.

### Worker errors

When the worker hits an orderly error, it tries to seal and sync the leaf-map and header-index
runtime allocators before exiting. This doesn't advance the durable height, send notifications
or write a clean marker. Both the original error and any failures while finalizing are
preserved.

### Known limitation

The underlying runtime database has a crash-recovery limitation that predates this design. A
hard kill or power loss during state application, before the allocator syncs, can leave
unfinished pages or unpublished bucket heads, and `open_runtime` may then refuse to reopen the
database. The publication protocol doesn't repair that database format.

- Losing an unpublished WAL and recovering a published WAL are covered by smoke tests that kill
  the writer.
- Recovery during database application is covered only by injected **orderly** failures. There
  is no guarantee of recovery from an arbitrary SIGKILL or power loss.

### Journal format compatibility

Legacy journals are imported once at startup into the publication format. A permanent
initialization header tells the two formats apart. On an initialized journal, a missing or
corrupt marker is an error. It never permits replaying an unpublished tail.

Keep `forest.journal`, `forest.journal.published` and any `forest.journal.forest-rows` together.
Don't downgrade to an older binary once the new journal format is in use.

- Version-3 records store their physical layout.
- Older records are bound once to a checksummed `.forest-rows` sidecar file before replay or
  before a resize resumes. An interrupted resize supplies its original row count.
- Histories that completed a resize under an older binary, without layout metadata, have
  ambiguous journal coordinates. If the original layout is unavailable, rebuild rather than
  assume the retained records are safe to replay.

## P2P server

Steady state also starts a P2PV2-only BIP183 proof server on `P2P_HOST`/`P2P_PORT`.

### Transport

The `bip324` transport performs the responder handshake and encrypts every packet after it.
There is no P2PV1 parser or fallback.

The version handshake advertises `NODE_WITNESS`, `NODE_P2P_V2` and `NODE_UTREEXO`. It does not
advertise `NODE_NETWORK` or `NODE_NETWORK_LIMITED`, and block `getdata` requests are not
served. Clients must get blocks from a separate Bitcoin peer.

### Peer limits

| Limit | Value |
| --- | --- |
| Inbound peers | at most 64 |
| Handshake | expires after 10 seconds; at most 1 MiB and 64 packets |
| Established peers | disconnected for packets over 256 KiB, oversized request batches, or more than 100 packets per second sustained |

Every minute, the node logs the total number of connected peers, grouped by their sanitized,
self-reported software name (for example `Floresta=10 Satoshi=10`).

### `getuproof` / `uproof`

BIP183 `uproof` and `getuproof` use the short IDs 29 and 30. `getuproof` requests are accepted
both as short IDs and as long commands.

The server accepts Floresta's field mask:

| Bit | Requests |
| --- | --- |
| 0 | targets |
| 1 | all proof hashes |
| 2 | all leaf data |

So `0x07` requests everything. When the all-hashes or all-leaves bit is unset, the
corresponding bitmap selects elements least-significant bit first, and an empty bitmap selects
none.

Stored proof targets already use the 63-row wire layout, and P2P serves them unchanged.
Physical or logical forest-row metadata must not trigger another translation.

### `getheaders`

`getheaders` requests are served directly from the position-addressed header file and hash
index:

- Responses contain at most 2,000 headers and honor the stop hash.
- They never go beyond the committed proof-index height that the version handshake advertised.
- An empty locator requests only the eligible stop header.
- RPC is used as a fallback only when the flat header index is unavailable.

## Esplora backend

The `esplora` feature replaces Bitcoin Core RPC reads with an Esplora backend. The mainnet
flat-forest prover and the P2P server are always compiled in.

The Esplora backend reads plain hexadecimal headers. It derives coinbase status from the
decoded transaction rather than from the status endpoint. HTTP failures, invalid hashes and
overflowing heights are returned as errors.

## Dependencies

- `rustreexo` 0.8.0 from crates.io, including the position-addressed Pollard cache APIs.
- `floresta-db` from <https://github.com/davidson-souza/floresta-db>, including the runtime
  batch, compaction and online body-capacity APIs.

The final review was verified against local rustreexo revision
`e6748e572cff55366982652bca3f3cae3f1922cf` and floresta-db revision
`29397816fcd9fbef415820e4dbef18ab98104fe8`. The committed manifests use remote dependencies,
not sibling checkout paths. Remote builds require rustreexo 0.8.0 and the corresponding
database changes to be published, and those weren't available during the review.

The old lockfiles that pointed at local dependencies were intentionally removed rather than
presented as valid resolutions of the remote dependencies. After the dependencies are
published, generate and commit both lockfiles:

```bash
cargo generate-lockfile
cargo generate-lockfile --manifest-path fuzz/Cargo.toml
cargo build --locked --release
```

CI and Docker generate a lockfile only when none exists, then build with `--locked`.

## Testing

### Fuzzing

`journal_codec` and `pollard_behavior` are the fuzz targets. `pollard_behavior` uses a cheap,
non-cryptographic `FastHash`, so its update loop doesn't call Bitcoin's SHA-256 hashing.

### Esplora

Esplora backend regression tests use isolated local HTTP fixtures and don't depend on public
Esplora servers being available.

### Interoperability

The final interoperability smoke test used the actual Floresta codecs at revision
`d302d68e2e4529bf330a0d293b9e82690361d412`, over an encrypted localhost connection to the
bridge. It exercised:

- all eight field masks
- multibyte bitmap selection
- both command encodings
- all compact script tags
- header, stop-hash and tip behavior
- service flags
- `ping`
- block `notfound`

The transport regression test also covers already-normalized high-bit targets with 27-row index
metadata, which must be served unchanged.
